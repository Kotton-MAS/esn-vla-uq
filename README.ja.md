# esn-vla-uq

Echo State Network とリッジ read-out、split conformal prediction による、
VLA (vision-language-action) ポリシーの**閉形式・アンサンブル不要な較正済み予測区間**。

被覆率保証は実 `openpi` ロールアウトで検証済みです。**失敗検知は本リリースの主張には
含みません** ([スコープ](#%E3%82%B9%E3%82%B3%E3%83%BC%E3%83%97) を参照)。

[English README](README.md)

> **本リポジトリが出す数値はすべて同梱の合成ロールアウトデータ由来です**
> (`source: "synthetic"`)。実 LIBERO の評価結果ではありません。合成データ生成器は
> 「単純なベースラインでは成否を完全には分離できない」よう意図的に調整してあります
> ([`docs/design.md`](docs/design.md) 7 節)。

## クイックスタート

```bash
uv sync
uv run esn-vla-uq calibrate     # 同梱の合成データで被覆率 / ECE
uv run esn-vla-uq diagnose      # スペクトル半径 / ESP / メモリ容量
```

サブコマンドは 4 つあります。

| コマンド          | 内容                                               |
| ----------------- | -------------------------------------------------- |
| `calibrate`       | conformal 予測区間・被覆率・reliability curve・ECE |
| `diagnose`        | リザバー診断 (スペクトル半径・ESP・メモリ容量)     |
| `gen-sample-data` | 同梱の合成ロールアウトを再生成する                 |
| `demo`            | 上のアニメーション (`[viz]` が要ります)            |

`calibrate` と `demo` は `--input` でデータセットを読みます。省略すると同梱の合成
データ、`.npz` を渡すと保存済みデータセット、**ディレクトリ**を渡すと収集した openpi
ロールアウトとして読みます。`diagnose` は `ESNConfig` からリザバーを構築するので
データセットを取らず、`gen-sample-data` は書き出す側です。

## 実 openpi ロールアウトを使う

openpi の評価スクリプトはロールアウトを保存しません (replay 動画を書くだけ) ので、
収集は別の手順になります。`scripts/collect_openpi_rollouts.py` が openpi の LIBERO
評価ループをなぞって state / action / action chunk を記録します。

```bash
# 1. openpi 側: policy server を起動 (openpi 側の環境)
cd path/to/openpi && uv run scripts/serve_policy.py --env LIBERO

# 2. LIBERO クライアント側 (openpi の examples/libero/.venv、Python 3.8)
python path/to/esn-vla-uq/scripts/collect_openpi_rollouts.py \
    --output-dir outputs/openpi_logs --task-suite-name libero_10

# 3. こちらへ戻る (Python 3.12)
uv run esn-vla-uq calibrate --input outputs/openpi_logs --split within_task
```

このスクリプト**だけ**が openpi と LIBERO を必要とし、wheel にも sdist にも含めて
いません。パッケージ本体は収集済みログを読むだけで、依存は numpy のみです。

## デモ

![失敗開始後に不確実性が立ち上がる](docs/assets/uncertainty_demo.gif)

```bash
uv sync --extra viz
uv run esn-vla-uq demo --output outputs/demo.gif
```

下段が conformal 予測区間の半幅、すなわちステップ単位の不確実性スコアです。
図のエピソードでは失敗開始の前後で 1.13 倍になります。

**これは合成データであり、この上昇は生成器の作りを反映したものです。** 実 openpi
ロールアウトでは同じ関係が成り立ちません ([スコープ](#%E3%82%B9%E3%82%B3%E3%83%BC%E3%83%97))。デモが示すのは
出力の見え方であって、スコアが失敗を予測することではありません。

跳ね幅が控えめなのは**設計上そうしている**ためです。幅は最大 2 倍の範囲に収まるよう
有界にしてあり、観測量のレンジに引きずられないようにしています (下記)。失敗検知が
使うのは不確実性スコアの**順序**であり、この有界化では順序は変わりません。

> **この不確実性は失敗への「反応」であって「予兆」ではありません。**
> 立ち上がるのは失敗開始の **15 ステップ後**で、直前ではありません。不確実性の材料
> であるチャンク分散は推論ステップ (16 ステップ間隔) でしか更新されないため、遅れは
> チャンク周期で上限が決まります。そもそも失敗条件が始まる前のチャンクには手がかりが
> ありません。`demo` コマンドは実行のたびに実測の `detection_lag_steps` を出力します。

## しくみ

ロールアウトから固有受容感覚・実行された行動・ポリシーの action chunk が得られます。
ESN がその履歴をリザバー状態へ写像し、リッジ read-out が次ステップの行動を予測し、
split conformal が残差を有限標本の被覆率保証つき予測区間に変えます。区間の半幅が
そのまま不確実性スコアになります。

リザバーは固定のランダム行列で、学習するのは線形 read-out だけ (閉形式)。アンサンブルも
勾配学習も使いません。これが将来の物理リザバーへの移植可能性を支えています。

## 同梱の合成データでの結果

名目被覆率 90%、20 通りの較正/テスト分割の平均:

| スコア       | 区間幅             | 被覆率          | ECE    | 平均半幅   |
| ------------ | ------------------ | --------------- | ------ | ---------- |
| `absolute`   | 全ステップで一定   | 0.8945 ± 0.0309 | 0.0134 | 0.0432     |
| `normalized` | ステップごとに変化 | 0.8846 ± 0.0362 | 0.0269 | **0.0423** |

`normalized` はより狭い平均幅とステップ単位の不確実性スコアを両立するので既定です。
被覆率の不足は分割間のばらつきの標準誤差より小さい値です。

## 実 openpi ロールアウトでの結果

4 回の収集すべてを `scripts/collect_openpi_rollouts.py` で実際の policy server から
取得しました。

| スイート         | split         | 被覆率              | ECE    | 平均半幅 |
| ---------------- | ------------- | ------------------- | ------ | -------- |
| `libero_spatial` | `within_task` | **0.9019 ± 0.0089** | 0.0022 | 0.195    |
| `libero_spatial` | `across_task` | 0.8906 ± 0.0486     | 0.0055 | 0.237    |
| `libero_10`      | `within_task` | 0.9044 ± 0.0240     | 0.0065 | 0.363    |
| `libero_10`      | `across_task` | **0.7929 ± 0.1033** | 0.0797 | 0.590    |

**被覆率は 4 回の収集すべてで保たれています。** 10 エピソードでは 0.881 ± 0.049
でしたが、100 エピソードで分散が約 1/5 に縮みました。「有効標本数はエピソード数」
という議論の予測どおりです。

**`across_task` は長期タスクで崩れます。** 較正集合とテスト集合が別のタスク分布から
来るため保証が転移しない、という交換可能性の議論どおりの挙動です。`libero_10` では
0.793 まで下がり ECE は 12 倍になります。既定を `within_task` にしている理由です。

**収集は再現しません。** pi0 は行動をサンプリングする (flow matching) ため、同じ
`--seed` でも軌道が変わります。`--seed` が固定するのは LIBERO の初期状態だけです。
収集済みログを入力にした解析は再現します。

## リザバーは何を担っているか

read-out が見るのは `[1, u, x]` (バイアス・生入力・リザバー状態) です。`u` には
`action[t]` が入り目標は `action[t+1]` なので、**パススルーだけで恒等写像を張れます**。
つまり「区間が狭い」ことは、それ自体ではリザバーが効いている証拠になりません。
`calibrate --readout` でアブレーションを回せます (`docs/design.md` 11 節)。

| 設計行列 | 何を測るか       | `[1, u, x]` 比の平均半幅                    |
| -------- | ---------------- | ------------------------------------------- |
| `[1, x]` | パススルーを外す | **1.35〜6.6 倍広い**。20 分割すべてで負ける |
| `[1, u]` | リザバーを外す   | 0.56〜1.12 倍。**向きがスイートで変わる**   |

**仕事の大半はパススルーが担っています。** パススルーを外すほうが、リザバーを外すより
はるかに悪化します。

**リザバー自体の寄与は 1 割程度で、符号も普遍ではありません。** `libero_10` では
7〜11% 狭くなりますが、`libero_spatial` では 17%、合成データでは 77% **広がります**。
しかもリザバーを大きくすると縮み、N=50 で最大、N=500 でほぼ消えます (11.6 節)。

ここから 2 つ、いずれも仮説を 1 つ失う形で分かりました。

- **リザバー診断は区間の質を予測しません。** スペクトル半径とリーク率を 15 点掃引すると
  メモリ容量は 6.4 倍動きますが、区間幅は 5% しか動きません。リザバーが**有るか無いか**
  のほうが 2〜3 倍大きく効きます。相関の向きも逆 (記憶が多いほど広い) で、タスク
  スイートを跨ぐと符号が反転します (13 節)。
- **`rho((1-a)I + aW)` は力学を要約しません。** 実効スペクトル半径が同じでもメモリ容量が
  2〜3 倍違います。リーク率は入力の駆動強度そのものも掛けており、その経路は `rho(A)` に
  現れないためです (13.5 節)。

### タスクが記憶を要らないのか、ESN が記憶下手なのか

上の 2 つのアブレーションでは、この区別が付きません。3 つ目で切れます——パススルーに
**ただの遅延線** `u[t-1], …, u[t-k]` を足して、効くかどうかを見ます
(`calibrate --input-lags k`、16 節)。平均半幅:

| `k`          | 合成       | `libero_spatial` | `libero_10` |
| ------------ | ---------- | ---------------- | ----------- |
| 0 (`[1, u]`) | 0.0250     | **0.1957**       | 0.3446      |
| 5            | **0.0048** | 0.2312           | **0.2876**  |
| リザバー     | 0.0431     | 0.2162           | 0.3096      |

**記憶に価値がある場面では、ただの遅延線がリザバーに勝ちます。** 合成データでは
遅延 1 本で幅が 4.4 倍縮み、**リザバーは遅延線の 9 倍広く、記憶なしにすら負けます**。
`libero_10` でも遅延 5 本で 16.5% 改善し、やはりリザバーより狭くなります。
`libero_spatial` では何も効かず、過去に価値がありません（遅延線もリザバーも
`[1, u]` に負けます）。

つまり答えは (a) ではなく **(b)** です。タスクは短い記憶（5 ステップ = 0.25 秒程度）を
要求しており、**ESN はその取り出し方として適切ではありません**。11.6 節（`N` を
増やすと効果が消える）もこれで説明が付きます——小さい `N` で効いていたのは記憶の
中身ではなく、read-out の表現力と推定分散の釣り合いでした。

**この課題設定では、区間幅を根拠にリザバーを正当化できません。** 本手法の価値は
conformal 層にあり、再帰にはありません。物理リザバーという動機を否定するものでは
なく、「ここでは線形の短期記憶で足りた」＝非線形性が効く設定はまだ見つかっていない、
ということです。

スイートを跨いで転移した唯一の知見は、診断指標ではなくハイパーパラメータでした。
非リーク型 (`leak_rate=1.0`) が両スイートで最も悪い設定だった (13.8 節) ——
**ただし、そこで掃引した正則化強度の範囲でだけです。** `ridge_alpha=1` まで含めて
掃引すると、リーク率の効きの向きが反転します (15.3 節)。\*\*2 つのハイパーパラメータは
独立に効きません。\*\*片方だけの掃引から、もう片方をどちらへ動かすべきかは読めません。

既定値 (`leak_rate=0.7`、`ridge_alpha=1.0`) は、どれか 1 つのデータでの最良値ではなく
**4 データセットで最も外さない組**として選びました。どのデータでも良い組は存在せず、
この組でもどこかで最良から 24% 離れます (15 節)。**出発点であって、詰めた値では
ありません。**

## スコープ

**本リリースが確立したもの**: 有限標本の被覆率保証を持つ予測区間 (実 openpi
ロールアウトで検証済み)、およびリザバー診断。

**確立していないもの**: 不確実性スコアが失敗を検知すること。`calibrate` は失敗検知
AUROC を出力し続けますが、**探索的な診断値**です。実 openpi ロールアウトでは偶然と
同じ水準で、合成データの高い値 (0.87) は生成器がその関係を組み込んで作られている
ために出るものです。

これは点推定ではなく**区間**で決着させました。物体位置を記録した 615 エピソードで、
チャンク分散の AUROC は **0.475 [0.418, 0.533]**。実用の下限として置いた 0.6 を区間が
排除します。失敗様式ごとに分けても変わりません (`docs/design.md` 10.16 節)。

**ただし 1 つだけ排除できていません。** リザバー状態軌道の時間的特徴 (自己相関・
実効次元・新規性) を事前登録した規則で評価しました (14 節)。失敗の**瞬間**に対しては
0.463〜0.487 で 0.6 を排除する——「失敗直前に不確実性が跳ねる」という描像は支えられ
ません。しかしエピソード単位では `dropped` の新規性が 0.613 [0.533, 0.693] で、
**偶然は上回るが 0.6 を跨ぐ**。決着させるには概算でエピソード 1 万 6 千本が要り、
そもそも 0.6 は実用の下限です。したがって失敗検知は**否定ではなく未決**として記録し、
主張はしません。

失敗様式によって符号も変わります。掴んでから止まった失敗では軌道が潰れますが、
そもそも掴めなかった失敗では潰れません。**符号を固定した検知器は半分の場合に
間違えます。**

## リザバー診断

診断は付け足しではなく第一級の出力です。予測区間を信用してよいかを判断する前に、
リザバーの挙動を検査可能にするためのものです。

```bash
uv run esn-vla-uq diagnose --output-dir outputs/
```

```text
spectral: spectral_radius=0.900000 effective_spectral_radius=0.900000
esp: verdict=esp_holds sufficient(sigma_max<1)=False[1.784905] necessary(rho<1)=True[0.900000] ...
memory_capacity: total_mc=14.8294 mc_per_neuron=0.0741 memory_horizon=20 n_delays=200 ...
```

Echo State Property は単一の数値ではなく、**3 指標と総合判定**で報告します
(十分条件 sigma_max < 1、必要条件 rho < 1、経験的収束)。既定設定は必要条件を満たし
十分条件を満たしませんが、これは正常であり、3 つすべてを併記する理由でもあります。

メモリ容量は他の 2 指標と**同じリザバー**で測ります。当たり前に見えますが、最近まで
そうなっていませんでした。以前はスカラー入力のリザバーを別に建てて測っており、
`W_in` → `b` → `W` を 1 つの RNG から順に引く都合で、入力次元が違えば `W` まで別物に
なります。`--n-inputs 17` のレポートには、そのリザバーのスペクトル半径と**別の**
リザバーのメモリ容量が並んでいました。

**これらは健康診断であって、区間の質の予測子ではありません。** リザバーがまともな
領域にいるかは分かりますが、区間が狭くなるかは分かりません
([リザバーは何を担っているか](#%E3%83%AA%E3%82%B6%E3%83%90%E3%83%BC%E3%81%AF%E4%BD%95%E3%82%92%E6%8B%85%E3%81%A3%E3%81%A6%E3%81%84%E3%82%8B%E3%81%8B) を参照)。
