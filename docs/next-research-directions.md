## ① リザバーの存在証明アブレーション（**実施済み** → design.md 11 節）

**結果は `docs/design.md` 11 節に記録した。** 以下は依頼の内容と、実施して分かった
ことの要約である。

### ①の結論

- **仕事の大半はパススルーが担っていた。** `[1, x]`（パススルーを外す）はどの
  データでも最も広く、20 分割すべてで現行に負ける。疑い（`action[t+1] ≈ action[t]`
  の滑らかさで大半を説明できる）は**当たっていた**。
- **リザバーの寄与は小さく、スイートで向きが変わる。** libero_10 では幅が 7〜11%
  狭まるが、libero_spatial では 17%、合成データでは 77% **広がる**。
  「時間記憶が区間のシャープさを買う」は無条件には主張できない。
- **寄与は `N` が増えるほど 0 へ縮む。** `N=50` で最大（−11.6%）、`N=500` では
  ほぼ消える。「リザバーを大きくすれば効く」は成り立っていない。
- 判定は**対応のある差**で行った（同じ 20 分割の幅を引き算する）。すべての
  データセットで 2 標準誤差が 0 を跨がない。
- 副産物 1: **既定の `ridge_alpha=1e-6` はリザバー有りの条件に対して弱すぎる。**
  最良化しないと結論の向きが逆に出る。既定値の見直しは別タスク。
- 副産物 2: **失敗検知 AUROC は設計行列に依存しない**（3 条件で完全一致）。
  条件が変えるのは `q` と `c_j` という定数倍だけで、順位は動かないため。
  **リザバーを改良しても、この設計のままでは検知は動かない**（④に効く）。

### ①で入れたもの

| 追加                                              | 場所                       |
| ------------------------------------------------- | -------------------------- |
| `ESNConfig.use_reservoir` と 3 条件の名前         | `esn/config.py`            |
| `RidgeReadout(use_states=)`                       | `esn/readout.py`           |
| リザバーを駆動しない baseline 経路                | `uncertainty/conformal.py` |
| `calibrate --readout`                             | `calibration/commands.py`  |
| `std_interval_width` / `per_split_interval_width` | `calibration/report.py`    |

`per_split_interval_width` は②でも要る（格子点間の幅の差を対応のある差で見る）。

### ①から出た次の候補

- 既定 `ridge_alpha` の見直し。`N=200` なら 100 付近が要る。既定を変えると過去の
  レポートの数値が全部動くので、独立したタスクにする。
- タスクスイートを増やす。「長時間タスクではリザバーが効く」は 2 点を結んだ線
  でしかない。

## ② 診断指標 ↔ 較正性能の架橋（v0.3 本命）

### ②の現状

**先に潰すべき前提がある。診断しているリザバーと較正しているリザバーは別物である。**

- メモリ容量は `MEMORY_CAPACITY_INPUT_DIM = 1` に固定して測る
  （`diagnostics/runner.py`）。一方 `calibrate` の入力次元は `D_u = 17`（9.1 節）。
- `Reservoir` は `W_in → b → W` の順に同一 RNG から引く（`esn/reservoir.py`）。
  **`n_inputs` が変われば `W` まで別の行列になる。** 同じ `seed` でも同じリザバーに
  ならない。
- `spectral` / `esp` は `diagnose --n-inputs 17` で揃えられるが、MC は現状揃えられない。

したがって「MC が高いリザバーは区間が狭い」を今のまま測ると、**別々のリザバーの
数値を突き合わせることになる。** ここが②の最初のブロッカーであり、記事にする前に
必ず解く。

掃引の軸についても補正がある。`spectral_radius` と `leak_rate` は独立な 2 軸では
なく、実効ダイナミクスを決めるのは `A = (1-a)I + aW` の `rho(A)` である
（`diagnostics/spectral.py:effective_spectral_radius`、design.md 4.2 節）。診断側は
これを既に出力している。

掃引そのものは既存 CLI で回る。`calibrate` は `--spectral-radius` / `--leak-rate` /
`--n-reservoir` を持ち、レポート JSON に `esn_config` と `coverage` が入るので、
格子を回して JSON を集める外部スクリプトで足りる（③の washout を除いて新規フラグ不要）。

### ②のやること

1. MC を較正と同じ入力次元のリザバーで測れるようにする（`D_u` チャンネルの 1 本に
   スカラー信号を入れる、等）。**どのリザバーで測ったかを必ずレポートに残す**
   （`MemoryCapacityMeasurement.n_inputs` の既存の作法を踏襲する）。
2. `(spectral_radius, leak_rate)` の格子で `diagnose` と `calibrate` を対にして回す。
3. 横軸を `rho(A)`（実効スペクトル半径）に取って、MC・ESP マージン
   （`sigma_max(A)`、`decay_rate`）対 平均区間幅を描く。2 軸が `rho(A)` の 1 本に
   まとまるかどうか自体が結果になる。

### ②の判定

**点推定の相関だけで結論しない**（10.16 節で AUROC の点推定に頼って判断を保留した
のと同じ轍を踏む）。格子点ごとに `n_splits=20` の平均と std が出るので、
**格子間の幅の差が分割間ばらつきを超えるか**を基準にする。超えなければ
「診断指標では区間の質を予測できなかった」と記録する。

### ②のコスト

中。新規データ収集・GPU は不要。実装は MC の入力次元まわりのみ。掃引は CPU 時間で
足りる（`diagnose` は N=500 で 1 秒未満、`next-pr-candidates.md` の計測）。

## ③ タイムスケール設計の見直し（**washout は決着** → design.md 12 節）

### ③の結論（washout）

- **疑い 2（washout=100 で 2〜5 割破棄）は起きていなかった。** 較正経路の washout は
  0 で、1 標本も捨てていない。
- 逆向きの問い（過渡を入れたままで幅が広がっていないか）を測った結果、**washout を
  増やすと幅は単調に広がる**。捨てても被覆率は壊れないが、良くなることが無い。
- 理由が分かった。**エピソード先頭 20 標本の非適合度は、それ以降の約半分である**
  （比 0.518〜0.588、3 データすべてで 2SE 超）。初期過渡は予測しづらいどころか
  **最も予測しやすい区間**だった。washout は「最も易しい行を捨てる」操作になる。
- ESN の定石（初期過渡は read-out を歪めるので捨てる）は、**この予測タスクには
  当てはまらない**。定石が想定するのは長い 1 本の時系列で、150〜250 ステップの
  エピソードを多数並べた設定ではない。
- 配線の途中で不具合を 1 件見つけて直した（区間とラベルの行数がずれる。12.4 節）。

**決定: 既定の washout=0 を維持する。** `--washout` は掃引用に露出させた。

### ③の残り（leak_rate）

疑い 1（`leak_rate=1.0` は非リーク型で実効記憶が短い）は**未着手**。効き方は
`rho(A) = rho((1-a)I + aW)` を通るため、②の格子で `spectral_radius` と一緒に
掃引する。単独では測らない。

## ④ タイムアウト失敗 × 時間的特徴

### ④の現状

**「将来メモ」の段階ではない。前提の 2 つが既に確定している。**

1. **発動条件のうち「失敗数」は §10.16 で既に満たし、実行し、決着している。**
   615 エピソード・失敗 157 本を収集し、全失敗で AUROC 0.475 [0.418, 0.533]、
   実用水準 0.6 を排除した。失敗率を揃えたタスク限定の 120 本でも 0.488。
   「タスクあたり失敗 5〜10 本を集めてから」は**もう済んでいる**。
2. **「タイムアウト以外の失敗様式」は LIBERO では構造的に得られない**（§10.15）。
   `bddl_base_domain.py` の `done` は成功でしか立たず、失敗による早期終了条件が
   存在しない。したがってこの条件は「待てば揃う」ものではなく、**別の環境を
   用意する**という調達の話になる。

「瞬時量が無相関だったのは必然」という見立て自体は 10.11〜10.14 節と整合する。
ただし無相関はチャンク分散に限らず、`|a|`・`|Δa|` でも同じだった（10.14 節の表）。

**生きている種は §10.16 の残りものにある。** `dropped` の内訳から落下開始時刻が
取れており（中央値でエピソード長の 0.19〜0.38）、**実データでステップ単位の失敗時刻が
定義できたのはこれが初めて**である。リザバー状態軌道の自己相関・新規性低下を測るなら、
この時刻を「不確実性が上がるべき瞬間」の基準として使える。つまり④は待ちではなく、
**既に検証可能な状態にある**。

### ④のやること

- リザバー状態軌道の時間的特徴（自己相関の伸び、状態の実効次元の低下、新規性の減衰）を
  `dropped` の落下開始時刻に対して評価する。
- **回す前に排除水準と必要標本を決める。** 10.16 節と同じ形式（Hanley-McNeil、有効
  標本数はエピソード数）で、0.6 を排除できるかを事前に設計する。否定済みの検知タスクへの
  再挑戦であるため、事後に基準を動かさない。
- 失敗ラベルは閾値ヒューリスティックであってシミュレータの報告事実ではない
  （`data/failure_modes.py`、§10.15）。この但し書きは結果と一緒に持ち回る。
- 物体状態を ESN 入力に混ぜない線引きは維持する（§10.15）。リザバー状態は入力から
  作られるので抵触しないが、特徴設計の途中で物体位置を触らないよう注意する。

### ④の判定

区間で 0.6 を排除できなければ「時間的特徴でも検知できない」と記録し、失敗検知は
閉じる。10.16 節の結論に時間方向の 1 本を足して終わりにできる。

### ④のコスト

中。収集済みの `object_state` 付きコレクションで完結する。実装は状態軌道の特徴量と
評価スクリプト。
