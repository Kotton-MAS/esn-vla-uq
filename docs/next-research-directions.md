## ① リザバーの存在証明アブレーション（**実施済み** → design.md 11 節）

**結果は `docs/design.md` 11 節に記録した。** 以下は依頼の内容と、実施して分かった
ことの要約である。

### ①の結論

- **仕事の大半はパススルーが担っていた。** `[1, x]`（パススルーを外す）はどの
  データでも最も広く、20 分割すべてで現行に負ける。疑い（`action[t+1] ≈ action[t]`
  の滑らかさで大半を説明できる）は**当たっていた**。
- **リザバーの寄与は小さく、スイートで向きが変わる。** libero_10 では幅が 7〜11%
  狭まるが、libero_spatial では 17%、合成データでは 77% **広がる**。
  「時間記憶が区間のシャープさを買う」は無条件には主張できない。
- **寄与は `N` が増えるほど 0 へ縮む。** `N=50` で最大（−11.6%）、`N=500` では
  ほぼ消える。「リザバーを大きくすれば効く」は成り立っていない。
- 判定は**対応のある差**で行った（同じ 20 分割の幅を引き算する）。すべての
  データセットで 2 標準誤差が 0 を跨がない。
- 副産物 1: **既定の `ridge_alpha=1e-6` はリザバー有りの条件に対して弱すぎる。**
  最良化しないと結論の向きが逆に出る。既定値の見直しは別タスク。
- 副産物 2: **失敗検知 AUROC は設計行列に依存しない**（3 条件で完全一致）。
  条件が変えるのは `q` と `c_j` という定数倍だけで、順位は動かないため。
  **リザバーを改良しても、この設計のままでは検知は動かない**（④に効く）。

### ①で入れたもの

| 追加                                              | 場所                       |
| ------------------------------------------------- | -------------------------- |
| `ESNConfig.use_reservoir` と 3 条件の名前         | `esn/config.py`            |
| `RidgeReadout(use_states=)`                       | `esn/readout.py`           |
| リザバーを駆動しない baseline 経路                | `uncertainty/conformal.py` |
| `calibrate --readout`                             | `calibration/commands.py`  |
| `std_interval_width` / `per_split_interval_width` | `calibration/report.py`    |

`per_split_interval_width` は②でも要る（格子点間の幅の差を対応のある差で見る）。

### ①から出た次の候補

- 既定 `ridge_alpha` の見直し。`N=200` なら 100 付近が要る。既定を変えると過去の
  レポートの数値が全部動くので、独立したタスクにする。
- タスクスイートを増やす。「長時間タスクではリザバーが効く」は 2 点を結んだ線
  でしかない。

## ② 診断指標 ↔ 較正性能の架橋（**実施済み・仮説は否定** → design.md 13 節）

### ②の結論

- **ブロッカーは実在した。** MC は `D_u=1` の別リザバーで測っていた。同じ `seed`
  でも `n_inputs` が違えば `W` まで別物になるため、1 つのレポートに別々の
  リザバーの数値が並んでいた。同じリザバーで測るように直した。

- **「リザバーの力学が UQ の質を決める」は成り立たなかった。** `spectral_radius`
  × `leak_rate` の 15 点格子で **MC を 6.4 倍動かしても、幅は 5% しか動かない**。
  105 対中 24 対しか 2SE を超えない。

- **リザバーの有無のほうが 2〜3 倍大きい。** リザバー無し baseline は最悪の格子点
  よりさらに 8.8% 広い。①と合わせると「パススルーが主役、リザバーの有無が 1 割、
  どのリザバーかは誤差」という順になる。

- **相関の向きが逆だった。** MC が大きいほど区間は**広い**（Spearman +0.73）。
  記憶は設計行列の実効自由度を増やすだけで、このタスク（1 ステップ先の action）
  では使い道が無い。`ridge_alpha` を各点で最良化しても向きは変わらない。

- **`rho(A)` は力学を要約しない。** ②に着手する前に書いた補正（2 軸は `rho(A)` の
  1 本にまとまる）**自体が誤りだった**。`rho(A)` がほぼ同じでも MC は 2〜3 倍違う。
  リーク率 `a` は状態更新式で入力の駆動強度そのものを掛けており、その経路は
  `rho(A)` に現れない。

- **スイートを跨ぐと符号が反転する。** libero_spatial では MC の Spearman が
  +0.27、`rho(A)` は **−0.53**（l10 では +0.30）。どの指標も向きを共有しない。
  片方だけ見て一般化していたら 10.11 節と同じ誤りだった。

- spatial では**どの格子点もリザバー無し baseline に勝てない**（最良でも 2.9% 広い）。
  力学のチューニングでは 11 節の結論を覆せなかった。

**期待した「独自コンテンツ」は得られなかった。** 得られたのは否定的な知見である
（診断は健康診断としては機能するが、UQ の質の予測子ではない）。

### ②の残り

- `input_scaling` と `density` は動かしていない。MC を動かす軸は他にもある。
- `N=200` 固定（11.6 節で寄与が `N` に依存することが分かっている）。

## ③ タイムスケール設計の見直し（**washout は決着** → design.md 12 節）

### ③の結論（washout）

- **疑い 2（washout=100 で 2〜5 割破棄）は起きていなかった。** 較正経路の washout は
  0 で、1 標本も捨てていない。
- 逆向きの問い（過渡を入れたままで幅が広がっていないか）を測った結果、**washout を
  増やすと幅は単調に広がる**。捨てても被覆率は壊れないが、良くなることが無い。
- 理由が分かった。**エピソード先頭 20 標本の非適合度は、それ以降の約半分である**
  （比 0.518〜0.588、3 データすべてで 2SE 超）。初期過渡は予測しづらいどころか
  **最も予測しやすい区間**だった。washout は「最も易しい行を捨てる」操作になる。
- ESN の定石（初期過渡は read-out を歪めるので捨てる）は、**この予測タスクには
  当てはまらない**。定石が想定するのは長い 1 本の時系列で、150〜250 ステップの
  エピソードを多数並べた設定ではない。
- 配線の途中で不具合を 1 件見つけて直した（区間とラベルの行数がずれる。12.4 節）。

**決定: 既定の washout=0 を維持する。** `--washout` は掃引用に露出させた。

### ③の結論（leak_rate、②の格子で決着）

疑い 1（`leak_rate=1.0` は非リーク型で実効記憶が短い）は**方向として支持された**。

- **既定の `leak_rate=1.0` は、両スイートで最も悪いリーク率だった。**
  `a=0.5` にすると spatial で平均 8.2% 幅が縮み、5 点中 5 点で有意。l10 では
  `a=0.2` が平均 2.2% 改善（5 点中 2 点で有意）。
- **これが格子から得られた唯一の転移する知見である。** 診断指標ではなく、
  ハイパーパラメータそのものだった（design.md 13.8 節）。
- ただし最適な `a` はスイートで違う（l10 は 0.2、spatial は 0.5）。**既定値を
  決め打つ根拠は無い。** 変更は過去のレポートの数値を全部動かすので独立タスク。

なお「効き方は `rho(A)` を通る」と書いていたが、これは誤りだった（②の 13.5 節）。
`a` は状態更新式で入力の駆動強度そのものを掛けており、その経路は `rho(A)` に
現れない。

## ④ タイムアウト失敗 × 時間的特徴（**実施済み・未決** → design.md 14 節）

### ④の結論

回す前に判定規則を固定した（排除水準 0.6、有効標本数はエピソード数、設定は既定に
固定、**符号は事前に指定**）。物体位置を持つ 4 コレクション 415 エピソードで評価。

- **落下の「瞬間」は捉えられない。** `dropped` のエピソード内で落下開始以降を陽性に
  する最も鋭い検定では、3 特徴とも 0.463〜0.487 で **0.6 を区間で排除**する。
  デモ GIF が想定する「失敗直前に跳ねるバー」は時間的特徴でも支えられない。
- **エピソード単位では失敗様式で向きが逆になる。** `dropped`/`held_but_unplaced`
  では予測どおり（0.61〜0.67）だが、`never_lifted` では逆（0.45）。掴んでから
  止まった失敗と、そもそも掴めなかった失敗は軌道の見え方が反対である。混ぜると
  0.53〜0.56 に薄まる。
- **ただし排除もできない。** `dropped`/新規性は 0.613 [0.533, 0.693] で、0.5 は
  上回るが 0.6 を跨ぐ。**この計画で「排除できない」ものが出たのは初めて。**
- **標本を増やしても決着しない。** 0.6 の上下を分けるには `dropped` が約 38 倍
  （エピソード 1 万 6 千本規模）要る。しかも 0.6 は「無いよりまし」の下限であり、
  境界上の効果を精密化しても実用にはならない。

**決定: 失敗検知は「否定」ではなく「未決」として置く。** 10.14 節の「主張しない」を
維持する。時間的特徴を実装したが、これで検知できるとは主張しない。

### ④で入れたもの

| 追加                                                                    | 場所                        |
| ----------------------------------------------------------------------- | --------------------------- |
| `state_autocorrelation` / `state_participation_ratio` / `state_novelty` | `diagnostics/trajectory.py` |
| `auroc_confidence_interval`（Hanley-McNeil）                            | `calibration/metrics.py`    |
| `failure_mode_details`（エピソード単位の様式と落下開始時刻）            | `data/sources/openpi.py`    |

`auroc_confidence_interval` は 10.16 節の数値を再現する（テストで固定）。それまで
この計算はリポジトリの中に無かった。

### ④から出た次の候補

- 次に試すなら特徴ではなく**問題設定**を変える。`never_lifted` と `dropped` を
  1 つの「失敗」に混ぜている限り、向きが打ち消し合う。
- 失敗様式ごとに向きが逆になる事実は、**符号を固定した検知器を作ってはいけない**
  という設計上の制約として残る。

## ⑤ 遅延埋め込み baseline（**実施済み・答えは (b)** → design.md 16 節）

### ⑤がなぜ要るか

①②で「リザバーは幅をほとんど買わない」と分かったが、**その理由が切り分けられて
いない**。可能性は 2 つある。

- **(a) タスクが記憶を要求していない。** `action[t+1]` の予測がほぼマルコフ的で、
  過去情報に価値がない。→ **どんなリザバーを持ってきても原理的に効かない。**
- **(b) タスクは記憶を要求しているが、ESN という記憶の実装が下手。** → 時定数や
  非線形性の設計に改善余地がある。

`[1, u]` に単なる遅延線 `u[t-1], ..., u[t-k]` を足した baseline があれば、これが
一発で切れる。**遅延を足しても幅が縮まなければ (a)、縮むなら (b)。**

11.6 節の「`N=50` で効果最大、`N` を増やすと消える」も、(a) なら自然に説明が付く。
記憶の中身ではなく read-out の推定分散の話になるからである。

**この計画の中で最も安い実験である。** ラグ付き入力を設計行列に足すだけで、リザバーを
駆動する必要すら無い。

### ⑤で入れたもの

| 追加                                                                    | 場所                           |
| ----------------------------------------------------------------------- | ------------------------------ |
| `lag_segments`（エピソード境界を跨がない遅延埋め込み）                  | `uncertainty/conformal.py`     |
| `SplitConformalPredictor(input_lags=)` / `run_calibration(input_lags=)` | 同上 / `calibration/runner.py` |
| `calibrate --input-lags`                                                | `calibration/commands.py`      |

`ESNConfig` ではなく predictor 側に置いた。`washout` と同じ扱いで、`ESN.fit` では
効かない値を `ESNConfig` に足すと A3（効かないのに記録される）を悪化させるため。

**区間の先頭は端点保持で埋め、行は落とさない。** 行を落とすと 12.3 節（先頭は最も
予測しやすい区間）により残った行の非適合度が上がり、ラグを足した条件だけ幅が
系統的に広がる。全条件で同じ行を保つほうが比較として正しい。

### ⑤の結論

**データによって (a) と (b) に分かれ、(b) のほうが重い。**

| データ     | `[1, u]`   | 遅延線の最良     | リザバー | 答え    |
| ---------- | ---------- | ---------------- | -------- | ------- |
| 合成       | 0.0250     | **0.0048** (k=5) | 0.0431   | **(b)** |
| 実 spatial | **0.1957** | 0.1957 (k=0)     | 0.2162   | (a)     |
| 実 l10/pi0 | 0.3446     | **0.2876** (k=5) | 0.3096   | **(b)** |

- **記憶に価値がある場面では、ただの遅延線が ESN と同等以上。** 合成データでは遅延
  1 本で幅が 4.4 倍縮むのに、リザバーは遅延線の 9 倍広く、記憶なしにすら負ける。
  l10 でも遅延線がリザバーより狭い。
- **spatial では過去に価値が無い** (`k>=2` は有意に悪化)。ここは (a)。
- **必要な記憶は短い。** 最良は両データとも `k=5` 付近 (20 Hz なので 0.25 秒)。
  `k=20` では悪化する。診断の `memory_horizon`（21）はこのタスクには長すぎる。
- 11.6 節の「`N` を増やすと効果が消える」が説明できた。**効いていたのは記憶の中身
  ではなく、列を増やしたことによる read-out の表現力と推定分散の釣り合い。**

**この課題設定では、区間幅を根拠にリザバーを正当化できない**（16.5 節）。ただし
物理リザバーへの移植可能性と、他の目標量については否定していない。

### ⑤から出た次の候補

**次に手を入れるならリザバーの設計ではなく課題設定のほう。** 1 ステップ先の
`action` 予測は線形の短期記憶で足りてしまう。非線形性や長い記憶が本質的に要る
目標（長ホライズン予測など）でなければ、リザバーは正当化できない。

**5 項目に手を付け終えた。** ①②③⑤は決着し、④だけが未決として残る。

⑤が①②の結論を書き換えた。当初は「リザバーは予測区間には効くが（1 割）、失敗検知には
効かない」とまとめていたが、正しくは\*\*「記憶に価値がある場面でも、ただの遅延線が
ESN と同等以上」\*\*である。v0.1 以来の「予測区間としては機能し、失敗検知としては
機能しない」（10.13 節）は変わらないが、**その『機能する』部分はリザバーではなく
conformal 層の手柄**だった、というのが 5 項目を通した結論になる。
